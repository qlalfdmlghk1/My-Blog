## 기획

### 한 줄 소개

> ✍️ 직접 입력 필요

### 왜 만드는가

- velog는 글을 쌓기엔 충분하지만, 발행 흐름 전체를 직접 설계해볼 수는 없음
- 이 프로젝트의 목표는 "블로그를 갖는 것"이 아니라 **인증 → 작성 → 저장 → 정적 페이지 재생성**으로 이어지는 발행 파이프라인을 직접 만드는 것
- 🔲 velog와의 관계: 자체 블로그를 메인으로 두고 velog는 유입용 유지 · canonical 태그로 중복 정리

### v1 핵심 기능 ✅

1. **글 목록 · 글 상세** — 정적 생성(ISR)
2. **관리자 로그인** — Firebase Auth, 계정 1개(본인)
3. **글 작성 / 수정 / 삭제** — 마크다운 직접 입력 + 실시간 미리보기
4. **이미지 업로드** — ~~Firebase Storage~~ → **Vercel Blob**(브라우저 → 스토어 직행), 붙여넣기 시 URL 자동 삽입
5. **임시저장(draft) / 발행(published)** 상태 분리
6. **태그 필터**
7. **다크 모드**
8. **RSS · sitemap.xml · OG 이미지 자동 생성**

### v1에서 하지 않는 것 ✅

- **WYSIWYG 에디터** — 툴바 · 드래그 · 자동저장까지 가면 블로그가 아니라 에디터를 만드는 프로젝트가 됨
- 댓글 — 필요해지면 giscus 지연 로드
- 검색 — v2
  - ▶ 구현: 글 전체 검색은 여전히 v2다. 다만 **용어 사전 안 검색은 들어갔다**(표제어 · 별칭 · 정의문 · 초성)
- 다중 사용자 / 권한 등급

## 기술 설계

> 상세 아키텍처 결정과 면접 답변은 별도 **기술 스펙 문서**로 분리 (3문서 원칙)

### 왜 Next.js인가 ✅

- 글이 Firestore에 있으므로 빌드 시점에 전체 글 목록을 알 수 없음 → 순수 SSG 불가
- **ISR**: 평소에는 미리 생성된 정적 HTML을 서빙하고, 발행 시점에만 해당 경로를 재생성
- 결과적으로 DB 기반이면서 정적 사이트의 응답 속도를 유지
- 이 요구사항은 Vite/CSR 조합으로는 성립하지 않음 → **프레임워크 선택의 근거가 기능적으로 존재하는 프로젝트**

> ✍️ 면접 답변: "포트폴리오 사이트는 의존성 0개 바닐라인데 블로그는 왜 Next.js인가?" → 전자는 단일 페이지 · 서버 데이터 없음이라 프레임워크가 해결할 문제 자체가 없었고, 후자는 '동적 데이터 + 정적 성능'이라는 상충 요구가 있어 ISR이 필요했다. 도구를 먼저 정하지 않고 요구사항에서 역산했다는 점을 강조.

### 데이터 구조 🔲

`posts/{postId}` — slug · title · content(markdown) · excerpt · category · **subcategory** · tags[] · coverImage · status(draft|published) · createdAt · updatedAt · publishedAt

- 조회수는 v2로 유예 (Firestore 쓰기 비용 · 봇 카운팅 문제)
- **구현 시 추가**: `category` — 디자인 섹션이 "글 1개당 카테고리 정확히 1개"를 요구하는데 원래 필드 목록에 빠져 있었다. 해당 항목이 🔲 미확정이므로 추가했다.
- ▶ 구현: `subcategory`도 **필수 필드**로 추가됐다. 보안 규칙이 `exists()`로 실재를 확인한다.
- ▶ 구현: 용어 사전은 글과 별개 컬렉션 — `dictionary/{slug}` · `dictionaryCategories/{slug}`. **문서 ID가 곧 slug**이라 본문이 만드는 `/dictionary#{slug}` 앵커가 가리킬 곳을 잃지 않는다.
- ▶ 구현: `coverImage`는 Firebase Storage가 아니라 **Vercel Blob URL**이다.

### 렌더링 전략 🔲

- 공개 페이지: ISR — 발행/수정 시 `revalidatePath`로 해당 경로만 갱신
- 관리자 페이지: 클라이언트 렌더 + 인증 가드 (검색엔진 노출 불필요)
- ▶ 구현: 목록 페이지 이동은 `?page=2`가 아니라 **`/page/2`**다. Server Component가 `searchParams`를 읽으면 라우트가 동적 렌더링으로 바뀌어 목록의 ISR 정적 생성이 사라진다.

### 마크다운 처리 🔲

- 파싱은 서버에서만 수행 → 파서를 클라이언트로 내려보내지 않음
- 코드 하이라이팅: **Shiki** (서버에서 HTML로 변환, 클라이언트 JS 0KB)
- 에디터 미리보기만 클라이언트 파서 사용 → 관리자 라우트로 코드 분할되어 공개 페이지 번들에 미포함
- ▶ 구현: 파서는 `marked`, 하이라이터는 `shiki`를 **직접** 쓴다 — 기술 스펙 문서에 적힌 remark/rehype 체인은 채택하지 않았다(패키지 7개 → 2개).
- ▶ 구현: 렌더 시점에 **용어 자동 링크**와 목차(h2 · h3)를 함께 만든다. 링크가 렌더 시점에 붙으므로 용어를 하나 추가하면 **발행 글 전체를 재생성**한다 — 어느 글인지는 본문을 전부 훑어야 알 수 있어 전량 무효화가 더 싸다.

### 보안 🔲

- Firestore 보안 규칙: published 글만 공개 읽기, 쓰기는 관리자 UID만 허용
- 클라이언트 검증에 의존하지 않음 — 보안 규칙이 최종 방어선
- ▶ 구현: 관리자 판별은 UID가 아니라 **admin 커스텀 클레임**이다 — 규칙 파일이 정적이 되고(배포 전 치환 단계 없음), 관리자를 바꿔도 규칙 재배포가 필요 없으며, 저장소에 계정 식별자가 남지 않는다.
- ▶ 구현: Server Action은 쓰지 않는다. 관리자 쓰기는 **브라우저의 Firestore SDK가 직접** 하고, `firestore.rules`가 클레임 · 필드 검증 · 참조 실재(`exists()`)를 확인한다. `AuthGuard`는 **보안이 아니라 UX**다.
- ▶ 구현: 서버 라우트는 **권한이 필요한 부수효과만** 맡는다 — `/api/revalidate` · `/api/blob-upload` · `/api/dictionary/extract` · `/api/slug/suggest`. 전부 `Authorization: Bearer <ID 토큰>`을 `verifyIdToken(token, true)`로 검증한다.

## 트러블슈팅

> ⚠️ 개발 중 **실제로 발생한 문제만** 그때그때 기록. 사후 재구성 금지.

- **업로드 토큰에 Firebase ID 토큰이 실려 나가던 경로** (#4) — `/api/blob-upload`의 비어 있던 `onUploadCompleted` 훅 때문에 라이브러리가 `callbackUrl`을 만들었고, 그 순간 admin 클레임이 든 ID 토큰이 발급 토큰에 실려 업로드 완료 웹훅 본문으로 되돌아 나갔다. `getCallbackUrl`이 `VERCEL=1`에서만 해석돼 **로컬에서는 재현되지 않는** 배포본 전용 노출. 훅을 지우는 쪽을 골랐다 — 본문이 no-op이었고, 지우면 토큰 페이로드와 공개 콜백 경로가 함께 사라진다.
- **정규식 백트래킹** (#12) — `\]\([^)]*\)`가 닫는 괄호 없는 입력에서 길이의 제곱으로 느려졌다. 실측 488KB 기준 30~46초 → **18ms**. 같은 패턴이 `autoExcerpt`에도 있어 함께 고쳤다.
- **`npm run dev`가 `listen EFAULT: bad address ... :::3000`으로 죽는 문제** — 와일드카드 바인딩(`::`·`0.0.0.0`)이 간헐적으로 EFAULT를 내는 것. 특정 인터페이스 주소로는 항상 성공하므로 `npm run dev:ipv4`로 우회. 자세한 진단은 README.
- **한글 낱말 경계** (#9) — `\b`가 한글에 없어 앞뒤가 글자면 무조건 막으면 `상태를`이 안 걸리고, 통과시키면 `상태관리`의 앞 두 글자에 링크가 걸린다. 앞은 글자/숫자 금지, 뒤는 **조사 허용 목록**(을/를/이/가/으로/에서/…)으로 해결.

## AI 활용

> AI를 **어디에 넣을지보다 어디에 넣지 않을지**를 먼저 정했다.
> 저장 · 발행 같은 자동 경로에는 모델을 끼우지 않는다 — 실패가 사용자 동작을 막고, 같은 입력에 다른 결과가 나오면 되돌릴 기준이 사라진다.
> 모델은 **사람이 버튼을 누르는 자리**에만 두고, 결과는 전부 사람이 확정한다.

### 1. 제품 안의 AI — Gemini 2.5 Flash ✅

호출 지점은 **두 곳뿐**이고, 둘 다 관리자가 버튼을 눌러야 돈다.

| 라우트 | 하는 일 | 트리거 |
|---|---|---|
| `POST /api/dictionary/extract` | 본문에서 용어 후보 추출 — 표제어 · 별칭 · 정의문 · 영어 slug | 발행 전 확인 화면의 `추출` 버튼 |
| `POST /api/slug/suggest` | 제목(+ 본문 앞 1,000자) → 영어 kebab-case slug | 글 작성 화면의 `영어로 추천` 버튼 |

**왜 서버 라우트를 거치는가**

- 관리 화면은 **클라이언트 렌더**다. 브라우저에서 모델을 직접 부르면 **API 키가 번들에 실린다**
- 서버 라우트 + 서버 전용 env(`GEMINI_API_KEY`, `NEXT_PUBLIC_` 접두사 없음)가 이 프로젝트 **최우선 규칙**("서버 전용 시크릿을 Client Component 경로에 도달시키지 않는다")을 지키는 유일한 방법
- `lib/gemini.server.ts` 최상단에 `import 'server-only'` — 클라이언트에서 import 하면 빌드가 깨져 즉시 검출된다
- 인증은 다른 라우트와 동일 — Firebase ID 토큰 + `admin` 커스텀 클레임. **AI 호출은 돈이 드는 동작**이라 인증이 특히 중요하다

**호출 설계**

- **SDK 없이 REST 직접 호출** — 필요한 게 "JSON 스키마를 강제한 생성" 하나뿐이라 의존성을 하나 더 늘릴 이유가 없다
- 키는 쿼리스트링이 아니라 **`x-goog-api-key` 헤더**로 — URL은 로그와 에러 리포트에 남는다
- **`responseSchema`로 JSON 강제 + `temperature` 0.2** — 자유 텍스트를 파싱하면 형식이 매번 흔들리고, 그 흔들림이 화면에서는 "가끔 이상하게 나온다"로만 보인다. 사전 항목 · slug은 같은 입력이면 같은 결과가 나와야 하는 용도다
- **타임아웃 2단** — 라우트의 `maxDuration`(30~60초)은 *함수 실행* 상한일 뿐 fetch를 끊지 않는다. 모델이 늦어지면 함수 슬롯을 플랫폼 타임아웃까지 붙잡고 화면에는 원인 없는 실패만 남는다 → `AbortSignal.timeout(25초)`로 **우리가 먼저 끊고 이유를 말한다**
- **실패를 원인별로 나눈다** — 503 키 없음 · 429 한도 초과(기다리면 됨) · 504 타임아웃(본문 줄이기) · 502 연결/해석 실패. 이 판단은 한 곳(`lib/gemini.server.ts`)에서만 내린다
- **입력 상한** — 본문 20,000자(넘으면 앞에서부터 자르고 "잘렸다"를 화면에 알림), 후보 최대 12개(더 뽑으면 사람이 확인하는 일이 추출보다 오래 걸린다), 별칭 길이 클램프(약 4,800자를 넘으면 색인 정규식이 실행 시점에 예외를 던져 발행 글 전체가 렌더 불능이 된다)

**사람과 AI의 경계**

- **AI는 제안만 한다.** 후보를 사람이 확인 · 수정한 뒤에만 사전에 등록된다
- **추출은 발행의 전제가 아니다.** 키가 없거나 호출이 실패해도 추출 버튼만 멈추고 발행 흐름은 그대로 돈다
- **중복은 서버에서 걷어낸다.** 표제어뿐 아니라 별칭 하나만 겹쳐도 같은 용어로 보고 "이미 있음"으로 표시하며 **기존 정의문을 덮어쓰지 않는다.** 판정에는 본문 자동 링크가 쓰는 색인을 그대로 쓴다 — 두 판정이 갈라지면 이미 링크가 걸리는 용어를 "새 후보"라고 다시 등록하게 된다
- **분류는 비운 채 제시한다** — 용어가 어느 분류에 속하는지는 사람만 안다

**slug만 AI를 쓰는 이유 — 스스로 뒤집은 결정**

발행 slug은 원래 한글을 **발음 그대로** 로마자로 옮겼다(`리팩토링` → `ripaektoring`). 근거는 "번역기를 물리면 키 · 비용 · 실패 폴백이 생기고, 같은 제목이 호출마다 다른 주소가 된다"였다. AI 제안 버튼은 그 근거를 셋 다 비껴간다.

1. **사람이 버튼을 눌러야** 부른다 → 저장 · 발행 경로에 AI 호출이 끼어들지 않는다
2. **실패해도 잃는 게 없다** → 기존 로마자 slug이 입력란에 그대로 남아 있다
3. **제안일 뿐이다** → 같은 제목에 다른 결과가 나와도 문제가 아니다. 확정은 사람이 한다

- 모델이 한글만 돌려주면 sanitize 후 빈 값이 된다. 그때 **로마자로 대신 채우지 않는다** — 버튼을 누른 사람은 영어 slug을 원한 것이고, 입력란에는 이미 로마자 값이 있다
- `slugify`(본문 제목 앵커용)는 건드리지 않았다. 그것까지 로마자로 바꾸면 이미 공유된 `#설치-방법` 링크가 한꺼번에 죽는다

> ✍️ 면접 답변: "AI를 어디에 썼나?" → 기능을 늘린 쪽이 아니라 **경계를 그은 쪽**으로 답한다. 호출 지점 2개, 둘 다 사람이 누르는 버튼, 결과는 전부 사람이 확정, 실패해도 본래 흐름은 멈추지 않음. 원래 로마자를 택했던 근거가 왜 이 경로에는 해당하지 않는지까지 설명한다.

### 2. 개발 과정의 AI — Claude Code ✅

`.claude/`에 팀 표준 체계를 두고 그 위에서 개발했다.

- `CLAUDE.md` — 진입점. 스택 rule과의 차이(rule은 FSD 전제, 이 프로젝트는 평면 구조)까지 명시해 **무엇을 강제하고 무엇을 안 하는지**를 못박음
- `rules/` — React/Next.js 규칙 · 보안 컴플라이언스(ISMS-P) 체크리스트 · 프로젝트 규칙
- `domain/taxonomy.md` — **유비쿼터스 언어.** 카테고리 · 팔레트 슬롯 · 태그 · 소주제 · 발행/임시의 정의와 *쓰지 말 것*("대분류" · "컬러 태그" · "서브카테고리")을 고정
- `hooks/` — 커밋 전 typecheck, 편집 후 포맷, 민감 파일(`.env` · `firestore.rules`) 편집 경고

**워크플로**: `/start`(plan.md · 이슈 · 브랜치 · progress.md) → `/plan-review`(기획 검수) → 구현 → `/review-converge`(리뷰 자가수렴) → `/commit` → `/pr`

- `/plan-review` — 정책 모순 · 미정의 케이스 · 흐름 누락을 "기획자에게 확인할 질문"으로 뽑는다. 이슈 #12는 **3차까지 돌려 '개발 착수 불가 0건'으로 수렴시킨 뒤** 착수했다
- `/review-converge` — 시니어 · 보안 · 아키텍트 · QA **4개 페르소나가 병렬로** diff를 리뷰 → 자동 반영(제한된 범위) → lint · typecheck · build 검증 → 재리뷰. Blocker 0건까지 반복
  - **자동 반영은 Blocker · 명백한 기능 오류 · 검증 실패로 범위를 제한**한다. 정책 판단(기본 선택 상태 · 에러 원문 노출 · rate limit · 인증 경로 변경)은 사람에게 넘긴다
  - 규칙 배포처럼 코드로 못 고치는 배포 작업도 사람 몫으로 남긴다

**수렴 루프가 실제로 잡은 것** — 커밋 41개 중 `리뷰 수렴 N라운드` 커밋이 **8개**다.

- 문구가 상태와 어긋난 세 곳 — 전부 성공했는데 "N개까지 등록한 뒤 멈췄습니다", 발행됐는데 "발행에 실패했습니다"
- 응답 계약이 두 곳에 선언돼 있던 문제 — 라우트와 클라이언트가 각자 타입을 선언하면 서버가 필드를 바꿔도 타입 에러가 나지 않고 `undefined`로만 드러난다

**루프가 만든 회귀도 남겼다** — 수렴 루프는 항상 단조 개선이 아니다. 2라운드가 넣은 "4칸 들여쓰기 = 코드블록" 한 줄이 중첩 목록과 목록에 딸린 설명 문단을 통째로 지웠고, 3라운드에서 되돌렸다. 정규식으로는 목록 문맥을 볼 수 없어 정확히 가를 수 없다 — **덜 지워 조금 과대집계하는 쪽**을 택했다.

> ✍️ 면접 답변 소재: AI로 코드를 빨리 쓰는 것보다 **틀린 코드를 걸러내는 절차**를 만드는 데 시간을 더 썼다. 무엇을 자동 반영하고 무엇을 사람에게 남길지 경계를 정해뒀고, 루프가 만든 회귀를 되돌린 기록까지 남겼다. 제품의 "모델은 사람이 버튼을 누르는 자리에만 둔다"와 같은 원칙이다 — **판단의 마지막 자리는 사람에게 남긴다.**

### 3. 기록 체계 ✅

- `docs/features/{feature}/plan.md` — 목적 · 범위 · 접근 방식 · 검증 계획 · 결정 사항
- `docs/features/{feature}/progress.md` — 커밋 단위로 **변경 요약 + 결정 로그 + 다음 작업**을 누적. *왜 그렇게 했는가*와 *왜 뒤집었는가*가 여기 남는다
- 이 문서의 갱신 재료도 전부 위 기록에서 나왔다

## 계획 → 실제로 뒤집힌 결정

> 계획이 틀렸다는 기록이 아니라 **근거가 바뀐 기록**이다. 원래 근거와 무엇이 달라졌는지를 함께 남긴다.

### 이미지 업로드: Firebase Storage → Vercel Blob

- **왜**: Firebase Storage가 2024년부터 Blaze(카드 등록)를 요구한다. Vercel Blob은 Hobby에서 카드 없이 무료 한도를 쓴다
- **덤으로 얻은 것**: 파일을 서버로 받지 않고 **브라우저 → 스토어 직행**으로 올린다 → 서버리스 본문 상한(4.5MB)을 피하고, 함수(`iad1`)와 스토어(`icn1`)의 리전 차이로 파일이 태평양을 두 번 건너는 것도 막는다
- **서버가 하는 일**: 파일이 아니라 **허가 토큰만** 내준다(`/api/blob-upload`). 크기 · 형식 제한도 서버가 정한다 — 클라이언트에서 거르면 `upload()` 직접 호출로 우회된다

### 카테고리: 코드 상수 6개 고정 → Firestore 컬렉션 + 관리 화면

- **왜**: 상수면 카테고리를 하나 늘릴 때 **코드 수정 + 보안 규칙의 하드코딩 목록 수정 + 규칙 재배포**가 함께 필요하고, 규칙을 잊으면 저장이 **조용히** 막혔다. 규칙은 이제 목록 대신 `exists(/categories/{slug})`로 확인한다
- **색은 자유 컬러피커가 아니라 팔레트 슬롯 12종**: 자유 색이면 라이트 배경 · 글자 · 다크 배경 · 글자 네 값을 사람이 맞춰야 하고 하나만 어긋나도 다크 모드에서 글자가 안 읽힌다. 슬롯은 네 값이 이미 짝지어져 있어 **무엇을 골라도 대비가 깨지지 않는다**
- **기본 6개 폴백은 넣었다가 제거했다**: 폴백을 두면 관리 화면에서 전부 지워도 되살아난다. 예시 6개는 `scripts/seed-categories.mjs`에만 있고 선택 사항이다
- 그래서 **"6개 고정"은 더 이상 코드가 강제하지 않는다.** 개수를 관리하는 것은 운영 원칙으로 남는다

### 분류 계층: 카테고리 1단 → 카테고리 → 소분류 2단

- 소분류는 `categories/{cat}/subcategories/{sub}` **하위 컬렉션**. slug 유일성이 카테고리 안에서만 필요하고(`프론트엔드/react` ↔ `백엔드/react`), 규칙의 `exists()` **한 번이 "존재"와 "그 카테고리 소속인가"를 동시에** 만족시킨다 — 부모를 필드로 두고 대조했다면 그 필드가 위조될 수 있었다
- **태그는 계층 밖의 가로축**으로 확정. 소분류가 트리의 두 번째 단을 가져갔다

### 좌측 분류 트리: v1 없음 → v1 도입

- 원래 근거("좌측 트리는 글 872개라서 성립한다")는 **자유 증식하는 태그** 기준이었다
- 카테고리는 개수가 관리되므로 **글 수와 무관하게 항목 수가 유지된다.** 글 0편 카테고리는 링크 없이 흐리게 처리

### 발행: 버튼 → 즉시 발행 → 버튼 → 확인 화면 → 확정

- 에디터가 **먼저 저장하고** 문서 ID로 넘긴다 → 이탈해도 내용이 남는다. 다만 상태는 올리지 않는다
- **`published`로 바꾸는 것은 확인 화면의 확정 버튼 하나뿐이다** — 수정 중이던 발행 글이 확인 화면을 여는 동안 내려가면 안 되기 때문
- 주소로 직접 들어올 수 있으므로 최소 기준(제목 · 본문 · slug · 분류)을 여기서 검증한다
- **AI 용어 추출이 붙는 자리**이기도 하다

### 목록 페이지 이동: `?page=2`가 아니라 `/page/2`

- Server Component가 `searchParams`를 읽으면 라우트가 **동적 렌더링으로 바뀌어 목록의 ISR 정적 생성이 사라진다**
- `generateStaticParams`는 2페이지부터 낸다. `01` · `2.0` · `+2`는 거른다 — 같은 페이지가 여러 주소로 열리면 검색엔진에 중복 문서로 잡힌다

### 용어 사전 (계획에 없던 축)

- **왜 별도 컬렉션인가**: 같은 용어를 여러 글에서 설명하면 설명이 조금씩 갈라지고 어느 쪽이 정본인지 알 수 없게 된다. 정의는 한 곳에 두고 글은 링크만 건다
- **왜 리포지토리 마크다운이 아닌 Firestore인가**: "웹에서 직접 작성"이라는 프로젝트 목표와 같은 축이고, 용어를 하나 늘릴 때마다 커밋 · 배포를 거치지 않는다
- **자동 링크는 렌더 시점에** 붙는다. 글 1편당 **첫 등장 한 번만** — 스무 번 걸면 본문이 링크 밭이 된다. 제목(h2/h3)과 기존 링크 안에서는 걸지 않는다(중첩 링크는 유효하지 않은 HTML)
- **공개 주소는 `/glossary` → `/dictionary`로 옮겼다.** 본문 링크는 렌더 시점에 붙으므로 기존 글은 재생성되며 따라오고, 밖에서 걸어둔 옛 주소는 `next.config.ts`의 영구 리다이렉트가 받는다

### 색 규칙의 의도된 예외 2건

원칙은 여전히 "색은 카테고리에만, 링크 · 버튼 · 본문은 무채색"이다. 다만 두 곳에서 의도적으로 예외를 뒀다.

- **용어 링크 밑줄 = 그 글의 카테고리 색.** 원칙이 막으려던 것은 *임의의 파랑*이 카테고리 색과 부딪혀 분류인지 링크인지 흐려지는 상황인데, 카테고리 색 자체를 쓰면 부딪힐 상대가 없다. 바꾸는 것은 밑줄색뿐이라 본문 글자 대비는 그대로다
- **드래그 선택색(형광펜).** 선택 영역은 '분류'가 아니라 '지금 짚은 곳'이라 카테고리 색과 경쟁하지 않고, 무채색이면 브라우저 기본 파랑과 구분되지 않는다. 글 상세는 그 글의 카테고리 색, 사전은 **항목마다** 그 용어의 분류 색, 분류 맥락이 없는 화면은 기본 노랑

### 폰트: Pretendard Variable → 티머니 둥근바람

- 본문 · 제목은 **티머니 둥근바람**(jsDelivr CDN, 웨이트 400 · 800), Pretendard는 폴백으로 유지. `preload` + `font-display: swap`으로 렌더 차단을 막았다
- 코드는 `D2Coding`. OG 이미지 생성에는 `Pretendard-Bold.woff`를 파일로 읽는다 — 코드 분석으로 추적되지 않아 `outputFileTracingIncludes`에 명시했다(빠지면 런타임에 `ENOENT`로 죽는다)
