- [x] `/dictionary` **검색** 추가 — 표제어 · 별칭 · 정의문까지 대상
- [x] 발행 글 하단에 **관련 용어 섹션** 추가 — `관련 용어 / - 용어1 : 링크` 형식
- [x] 카테고리별 밑줄 색을 **사전 페이지까지 확대** 적용
- [x] 드래그 선택 색도 같은 규칙으로 — 글 상세는 글의 카테고리 색, 사전 항목은 그 용어의 분류 색

## 🛠️ 접근 방식

- **AI 제공자: Gemini** (모델·키 보관은 구현 시 확정). 관리자 화면은 클라이언트 렌더이므로 **서버 라우트 경유** — `src/app/api/revalidate/route.ts` 의 Firebase ID 토큰 + admin 클레임 검증 패턴을 따른다
- 용어 분류는 글 카테고리(`categories`)와 **별개 컬렉션**. `Category` 가 팔레트 슬롯 ID 만 저장하는 방식(`src/lib/palette.ts`)을 그대로 따라 색을 다룬다
- 검색은 정의문까지 대상 — 전체 목록을 받아 클라이언트에서 필터할지 여부는 용어 수를 보고 구현 시 결정
- 기존 자산 재사용: `src/lib/dictionary.ts`(`groupDictionary`·`splitByDictionary`) · `dictionary.client.ts` · `dictionary.server.ts` · `src/lib/romanize.ts`

## ✅ 검증 계획

- 단위/통합 테스트: 테스트 스크립트 미도입 — `npm run lint` · `npm run typecheck` · `npm run build` 로 대체
- 회귀 포인트:
  - `firestore.rules` 의 `validDictionaryTerm` — `category` 는 선택 필드(빈 문자열 허용)라 기존 문서 수정이 막히지 않는다
  - 본문 자동 링크(`src/lib/markdown.ts` · `splitByDictionary`) — 용어 등록·분류 추가로 기존 링크가 깨지지 않는지
  - 발행 흐름 변경이 `draft`/`published` 상태 전환·`revalidatePost` 호출을 건너뛰지 않는지
  - Gemini API 키가 Client Component 경로로 새지 않는지 (`CLAUDE.md` 최우선 규칙)
  - 밑줄 색 확대 시 기존 글 상세의 `--term-line` 동작(커밋 fe5dec1)과 충돌하지 않는지
- 수동 확인:
  - 작성 → 발행 → 확인 페이지 → AI 추출 → 후보 수정 → 등록 → 발행 확정 → 글 하단 관련 용어·본문 링크 확인까지 한 번 주행
  - 중복 후보가 "이미 있음"으로 제외 표시되는지
  - 분류를 고르지 않고 등록 → 사전에서 '분류 없음'으로 모이고, 사전 관리에서 나중에 지정되는지
  - `/dictionary` 카테고리 필터 · 검색(표제어/별칭/정의문) · 결과 0건 표시
  - 다크/라이트 테마에서 용어 링크·사전 페이지 밑줄 가독성
